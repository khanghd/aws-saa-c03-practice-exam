Vì sao "Architecture" là từ khóa

Developer hỏi "gọi API thế nào?". Architect hỏi "với volume, budget, latency SLA, risk profile này, tổ hợp model/pattern/retrieval/guardrail nào phục vụ user tốt nhất?". Đáp án nhiễu thường chạy được về kỹ thuật nhưng lệch ràng buộc đề bài — ví dụ đề xuất agent tự chủ hoàn toàn cho việc mà 1 prompt chain 2 bước xử lý rẻ và dự đoán được hơn.

Phạm vi thi KHÔNG bao gồm

Fine-tuning · API auth/billing · deploy/host MCP server · chi tiết streaming · rate limit & pricing cụ thể · metric so sánh model · embeddings/vector DB · computer use · vision · chi tiết sâu prompt caching (chỉ cần biết feature tồn tại).

Cách đọc mỗi tình huống (architecture lens)

  • User thực sự cần outcome gì — tách khỏi cách triển khai cụ thể
  • Chi phí khi sai là bao nhiêu? (quy định/y tế khác hẳn gợi ý phim)
  • Luồng việc có đoán trước được không? Dự đoán được → workflow; mở, cần quyết định runtime → agent
  • Tool permission nào là tối thiểu cần thiết (least privilege)?
  • Làm sao biết hệ thống vẫn đúng sau khi đổi model/prompt/tool? → evaluation & monitoring
  • Dữ liệu cần lấy từ đâu — ảnh hưởng thiết kế retrieval/tool
Bẫy thường gặp: chọn phương án mạnh/tự chủ nhất "cho an toàn" (đề trừ điểm autonomy thừa); học thuộc tham số API thay vì lý luận trade-off; dùng thông tin logistics cũ về lệ phí/điều kiện thi.

1. Agentic Architecture & Orchestration 27%

Augmented LLM & nguyên tắc chủ đạo

Mọi thứ bắt đầu từ 1 đơn vị: augmented LLM — 1 model call tăng cường bằng retrieval, tool, memory. Nguyên tắc: tìm giải pháp đơn giản nhất có thể, chỉ tăng độ phức tạp khi cần — bắt đầu từ 1 lệnh gọi, rồi mới thêm retrieval → structured output → tool → agent khi use case thật sự cần.

Bẫy: nhầm routing (cổng phân loại, 1 đường cố định) với orchestrator-workers (planner sinh nhiều subtask động); nhầm parallelization (subtask cố định, chạy song song) với orchestrator-workers (subtask khám phá lúc runtime); nhầm evaluator-optimizer (lặp theo feedback chất lượng) với routing (quyết định 1 lần).

Workflow hay Agent?

Tín hiệu trong tình huốngNghiêng WorkflowNghiêng Agent
Các bước đã biết trướcCóKhông
Số bước đổi theo inputKhôngCó
Chi phí sai cao / bị quy địnhCó (dễ bound & audit)Chỉ khi guardrail chặt

Agent đúng khi có đủ 3 guardrail: stopping condition (giới hạn turn/budget), sandboxing (cô lập action khỏi production), human checkpoint (duyệt plan/diff trước hành động không hoàn tác). Thiếu cả 3 → thường là distractor.

Vòng lặp Agentic (3 giai đoạn)

1. Gather context→ 2. Take action (tool_use)→ 3. Verify the work→ lặp lại tới stop condition

Dừng khi: task được verify xong, hết turn/token budget, tool lỗi terminal, hoặc human từ chối approval. Verify là giai đoạn hay bị bỏ quên nhất — agent báo thành công mà không kiểm tra gây "confident-but-wrong" / "hallucinate progress".

Verify đúng cách

  • Code agent: chạy test/linter sau mỗi edit (PostToolUse hook, tất định)
  • Retrieval/Q&A: yêu cầu trích dẫn passage; cài eval question "không có đáp án" để test abstain
  • Agent rủi ro cao: reviewer fresh-context riêng (model tự phê bình transcript dài của chính nó dễ thiên vị)

Stopping conditions

  • Max turns / max tool calls
  • Token/cost budget (model "thấy" đếm ngược) — khác max_tokens (trần cứng 1 response, model không biết)
  • Success check lập trình (test pass, schema valid)
  • Timeout wall-clock

Multi-agent: khi nào hợp lý

1 agent là mặc định. Chỉ thêm agent thứ 2 khi ≥1 điều đúng: task phân rã thành subtask độc lập chạy song song được; subtask cần tool/quyền khác nhau; subtask sẽ làm ngập context chính; subtask cần context "sạch" không thiên vị (vd reviewer không thấy lý luận của author).

Subagent = công cụ quản lý context, không chỉ song song hóa

Ví dụ: tổng hợp 5 bản review × 8.000 token. Nạp hết vào 1 agent = 40.000 token loãng. Sinh 5 subagent, mỗi cái đọc 8.000 token riêng, trả tóm tắt 300 token → orchestrator chỉ giữ ~1.500 token chắt lọc.

Pattern phổ biến nhất: orchestrator (hub-and-spoke) — 1 lead chia task, giao subagent, tổng hợp kết quả gọn (không phải full transcript). Delegation thường chỉ sâu 1 cấp — subagent tự sinh subagent khó bound hơn.

Error propagation: lỗi subagent phải nổi lên orchestrator dưới dạng kết quả có cấu trúc để retry/reassign/escalate — không được để subtask fail âm thầm, context ngập output thô, hay 2 subagent edit xung đột cùng resource (serialize write / chia phạm vi riêng).

Session management

Messages API tự nó stateless. Agent SDK sessions lưu/resume theo ID cho task dài nhiều ngày; memory qua các session (sở thích, fact đã học) nên lưu vào memory store riêng, không dựa in-context history.

Luồng 1 tool call thực tế

Claude phát tool_use {name, input}→ code validate schema + auth→ thực thi, trả tool_result→ Claude đọc kết quả, tiếp tục

Claude không tự thực thi tool — model đề xuất, code tin cậy của bạn thực hiện. 2 chi tiết hay hỏi: (1) nhiều tool_use song song trong 1 response phải trả về cùng 1 user message gồm các tool_result (tách message sẽ "dạy" Claude ngừng gọi song song); (2) tool lỗi trả is_error: true, không được bỏ qua.

Bẫy MCP phổ biến nhất: nhầm resource (context chỉ đọc, không đổi state) với tool (hành động đổi state). Lấy schema/log cho context → resource; "làm gì đó" → tool.

Transport = quyết định trust-boundary

stdio

Subprocess local, chạy quyền máy user. Ranh giới là máy local — dùng cho truy cập file/process local.

Streamable HTTP

Dịch vụ remote qua mạng — cần authentication & scoping vì bề mặt tấn công lớn hơn.

Least privilege & confused-deputy

Tách read/write thành 2 tool authorize riêng để 1 call lỗi không leo thang từ lookup thành phá hoại. Coi model như "planner" không tin cậy (có thể bị prompt-injection từ text retrieved) — executor, không phải prompt, là nơi áp luật ai-được-làm-gì. Không bao giờ đưa raw secret vào context window (tránh bị echo lại); credential MCP lưu ngoài tầm model (vault/env substitution), inject ở egress.

Permission & Hook

Permission khớp theo blast radius: tool read-only → allow thoải mái; hành động phá hoại (rm -rf, git push --force, deploy production) → ask hoặc deny. Hook thêm lớp tất định model không thể bỏ qua: PreToolUse chặn lệnh khớp pattern (exit code ≠ 0 → chặn hành động); PostToolUse tự chạy linter/test sau mỗi edit.

Skills vs CLAUDE.md

Skill = SKILL.md với frontmatter (tên + description = trigger) + file hỗ trợ. Description chi phí thấp nằm sẵn trong context; toàn bộ skill chỉ nạp khi task khớp trigger (progressive disclosure). Dùng skill cho kiến thức đặc thù-theo-task, nạp-theo-yêu-cầu; dùng CLAUDE.md cho rule luôn-bật, ổn định.

Headless & CI

Chạy claude -p "..." trong CI cần: tiêu chí thành công rõ ràng, quyền hạn chế (không --dangerously-skip-permissions tràn lan ngoài sandbox), và validation tự động. Mỗi automation nên kết thúc bằng 1 bước validate cụ thể chứng minh thay đổi đúng.

Thất bại prompt yếu phổ biến nhất: chỉ dẫn mơ hồ ("summarize this nicely") để ngỏ output shape & hành vi khi lỗi → downstream không tin cậy được.

Cấu trúc Claude phản hồi tốt

XML delimiters

Tag như <document>, <instructions> ngăn nhầm dữ liệu với chỉ dẫn — phòng prompt injection từ nội dung retrieved.

Rule gần cuối prompt

Hiệu ứng recency: rule ngắn gọn đặt gần cuối được tuân theo chắc hơn đặt giữa prompt.

Cho model lối thoát ("tôi không biết" / sentinel value) thay vì ép bịa. Đặt context: rule ổn định ở system prompt, task tức thời ở cuối; phần đổi theo mỗi request đặt muộn để không phá cache prefix ổn định (xem Domain 5).

Few-shot example

Đa dạng thắng số lượng — 3-4 ví dụ đa dạng + 1 edge case khó thắng 10 ví dụ gần giống nhau. Không thay thế validation — model có thể viết văn xuôi thuyết phục mà vẫn vi phạm hợp đồng; code downstream vẫn phải validate object đã parse.

Bẫy: 1 prompt rõ ràng, cấu trúc tốt thắng 1 chain phức tạp khi task đơn giản — đáp án prompting over-engineered là distractor kinh điển.

Schema-first cho Structured Output

Thiết kế JSON schema trước prompt: field bắt buộc, enum, object lồng, và điều gì xảy ra khi validation fail — rồi viết prompt xoay quanh hợp đồng đó. Ngăn thất bại "đọc hay nhưng phá parser". Ràng buộc số/độ dài/đệ quy nên enforce trong code validation sau khi parse, không nhét hết vào schema.

Thực thi lập trình vs. hướng dẫn qua prompt

Cách tiếp cậnĐộ tin cậy
Hướng dẫn qua prompt ("please respond in JSON")Yếu nhất — vẫn có thể drift

Luôn định nghĩa đường lỗi sau N lần retry fail: default an toàn, escalate human, hoặc lỗi có kiểu — không bao giờ gửi output chưa validate xuống downstream.

Eval phải phủ cả đường lỗi

Bẫy phổ biến nhất: đáp án chỉ eval "happy path". Eval set thật cần: yêu cầu mơ hồ, tool lỗi/timeout, JSON không parse được, retrieval cũ/rỗng, prompt adversarial.

Chạy eval như regression gate: version-controlled, chạy trước & sau mỗi thay đổi ảnh hưởng chất lượng (nâng cấp model, sửa prompt, thêm tool/MCP, đổi retrieval). Điểm giảm → chặn/gắn cờ trước khi tới user. Ưu tiên regression eval hơn chỉ-thêm-retry hay đọc output bằng tay.

5. Context Management & Reliability 15%

Context là ngân sách

Claude coi trọng chỉ dẫn gần đầu (system prompt) và gần cuối (turn gần nhất) hơn — đặt rule lâu dài ở system prompt, task tức thời ở cuối. Fact hay đổi (giá, tồn kho, policy) → lấy tại thời điểm request, ground kèm trích dẫn, đừng nướng cứng vào prompt tĩnh.

Prompt Caching — cơ chế & bẫy

Cache key = byte chính xác của prefix tới điểm ngắt cache_control, theo thứ tự render tools → system → messages. Đổi 1 byte bất kỳ trong prefix → mất cache mọi thứ sau nó.

Giữ cache sống

  • Nội dung dễ đổi (timestamp, request ID) đặt sau điểm ngắt cuối
  • Không đổi tool list hay model giữa hội thoại
  • Xác nhận hoạt động: cache-read token > 0 qua các request cùng prefix

Giới hạn

  • Chỉ giúp context tĩnh, lặp lại — không giúp nội dung đổi mỗi request
  • 1 lần ghi cache tốn hơn đọc thường — chỉ đáng khi prefix tái dùng đủ nhiều

Compaction vs Progressive Summarization vs Context Editing

Kỹ thuậtLàm gì
Compaction (server-side)Tóm tắt turn cũ khi gần chạm limit; phải mang theo compaction block cho request sau
Progressive summarizationGiữ 1 summary "chạy", cập nhật sau mỗi cụm turn, bỏ turn thô cũ nhất
Context editing / clearingXóa hẳn tool result/thinking block cũ không còn liên quan (khác tóm tắt)

Phân biệt: compaction & summarization cô đọng; context editing xóa hẳn; caching tái dùng.

Nuance hay hỏi: retry chỉ dành cho lỗi tạm thời. Retry 1 lỗi tất định (schema sai, credential sai, 400 invalid-request) chỉ tốn token — sửa nguyên nhân, đừng retry.

Grounding vs Guardrail

Grounding giải quyết độ trung thực (câu trả lời có nguồn hỗ trợ không?) — retrieve context đáng tin, chỉ thị chỉ trả lời từ tài liệu cung cấp, cho phép "tôi không biết". Guardrail giải quyết an toàn & policy (câu trả lời có được phép tồn tại không?) — classifier/rule check chặn response sai policy trước khi tới user. 1 câu trả lời grounded hoàn hảo vẫn có thể sai policy; 1 câu trả lời an toàn vẫn có thể là bịa đặt. Đề thi ưu tiên đáp án nhiều lớp (ground + guardrail + validate) hơn 1 "viên đạn bạc".

3 câu hỏi trước khi chốt đáp án

  • Đáp án có khớp đúng với ràng buộc cụ thể của tình huống (volume, latency, cost, risk), không phải "giải pháp mạnh nhất nói chung"?
  • Rủi ro được kiểm soát bằng process/code tất định (schema, hook, eval gate), hay chỉ bằng lời dặn Claude?
  • Mức độ phức tạp (agent, multi-agent, kỹ thuật nâng cao) có thật sự xứng đáng với task, hay đơn giản hơn đã đủ?
Đây là tài liệu ôn tập cá nhân, tự biên soạn dựa trên outline công khai của kỳ thi, không liên kết hay được xác nhận bởi đơn vị tổ chức kỳ thi. Tên chứng chỉ/kỳ thi chỉ dùng để mô tả nội dung ôn tập, không hàm ý được tài trợ hay phê duyệt.
